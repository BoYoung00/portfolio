PROBLEM
  • 배포할 때마다 개발자가 Docker 이미지를 직접 빌드해 .tar 파일로 저장하고, 고객사 PC에 원격으로 접속해 그 파일을 옮긴 뒤 명령어로 설치·교체했습니다. 한 번에 20~30분이 걸렸고 버전 이력도 남지 않았습니다.

설계

  • 처음에는 WSL 안에 HTTP 에이전트를 두는 구조였지만, 첫날 Rust가 wsl.exe를 직접 실행하는 구조로 바꿨습니다. 스크립트는 표준 입력으로 넘겨 명령 주입과 명령줄 노출을 피했고, 서비스별 운영 스크립트(run.sh)가 상태·진행률·종료 코드를 정해진 형식으로 돌려줍니다.
  • 안전한 업데이트: 새 컨테이너가 헬스체크를 통과해야만 버전 파일을 기록하고, 실패하면 직전 버전으로 자동 복구합니다. 롤백 가능 여부는 화면이 아니라 스크립트 한 곳이 판단합니다.
  • 컨테이너는 살아 있는데 앱은 죽은 상태: AI 검사 엔진(GUI 프로그램)이 주기적으로 남기는 생존 신호로 실제 실행 여부를 판정하고, 신호가 끊기면 자동 정지 후 이력을 남깁니다. 이 과정에서 생긴 경쟁 조건 두 건(이전 세션 신호 파일, 업데이트 중 폴링)도 찾아 막았습니다.
  • 운영 스크립트도 앱처럼 배포: 실제로 Docker 이미지를 받고 컨테이너를 교체하는 건 고객사마다 다른 run.sh이고, 앱은 그걸 실행하는 버튼입니다. 그래서 고객사별 run.sh를 앱 저장소 한 곳에 모으고, Actions 한 번이면 고객사 PC WSL 안까지 백그라운드로 반영되게 했습니다. 스크립트를 고칠 때도 원격 접속이 필요 없고, 앱 재시작도 없습니다.
  • 작업 이력으로 원인 찾기: 버튼 실행마다 stdout·stderr를 고객사 PC의 작업 이력에 남겨(90일·최대 500건 보관 후 자동 정리), "업데이트가 안 된다"는 연락이 오면 원격으로 접속해 명령을 다시 돌려 보지 않고 앱의 개발자용 화면에서 바로 원인을 확인합니다.
  • WSL 호출은 두 개씩만 병렬로, 버전 조회는 화면을 먼저 그린 뒤 뒤에서 가져와 앱이 멈춘 것처럼 보이지 않게 했습니다.

보안

  • 토큰을 실행 파일에서 걷어냈습니다. 고객사별 토큰은 setup 전용 모드에서만 입력받아 Windows DPAPI로 암호화 저장합니다. 덕분에 하나의 실행 파일을 모든 고객사에 공개 릴리즈로 배포할 수 있게 됐습니다.
  • 서명된 업데이트만 설치: 앱은 공개 저장소에서 새 버전을 받아 스스로 업데이트합니다. 그래서 GitHub Actions가 빌드한 실행 파일에 서명 키로 서명해 올리고, 앱은 앱 안의 공개 키로 서명을 확인한 파일만 설치하게 했습니다. 누군가 저장소에 가짜 실행 파일을 올려도 고객사 PC에 자동으로 깔리지 않습니다.
  • 컨테이너 레지스트리 로그인은 매번 임시 설정 폴더에서 하고 지워, WSL 안에 자격 증명이 남지 않습니다. 운영 스크립트 묶음은 SHA-256 검증, 허용된 경로에만 기록, 원자적 교체로 적용합니다.

배포 파이프라인 세 갈래

  • 웹·API는 고객사별 브랜치 4개를 단일 브랜치 + 고객사 설정 파일로 합치고, 고객사별 이미지를 matrix로 빌드합니다. 테스트를 마친 이미지를 그대로 승격하므로 검증한 바이너리와 배포 바이너리가 같습니다.

  3. 이 설정을 풀려면 회사 모든 사이트에 영향을 주는 보안 정책을 바꿔야 해서 맞지 않다고 판단했습니다. 대신 팀 공용 계정의 OneDrive는 외부 공유가 따로 허용된다는 것을 찾아, 로그인 없이 열리는지와 같은 폴더의 다른 파일은 보이지 않는지까지 확인한 뒤 OneDrive로 바꿨습니다.

  • Microsoft 클라우드 권한은 SharePoint 사이트 1개 범위로만 신청했습니다. 승인 결과가 "성공"이었는데 실제로는 회사 전체 최상위 사이트에 부여된 것을 식별자 비교로 찾아내 당일 회수를 요청했고, 제 안내서에 빠져 있던 확인 단계를 추가했습니다.
  • 공유 링크는 30일 뒤 자동으로 만료되고, 31일이 지난 파일은 저장소에서 자동으로 지워 외부에 노출되는 기간과 저장 용량을 함께 관리합니다. 별도 스케줄러 없이 링크를 만들 때 하루 한 번만 정리가 돌게 했습니다.

  • 측정 조건(모바일, 느린 4G, 저사양 기기 에뮬레이션), 도구별 역할, 지표 우선순위(TBT·LCP·CLS), 완료 기준(70점 이상, LCP 4초 미만, TBT 600ms 미만, CLS 0.1 이하)을 표로 정리하고 29개 화면을 진단했습니다.
  • 3,678줄짜리 단일 페이지 파일을 28개 파일로 나눈 뒤 측정하면서 고쳤습니다. 최적화하기 좋은 구조를 먼저 만드는 것이 목적이었고, 테스트를 붙일 수 있는 구조로 가는 첫 단계이기도 했습니다.

원인별로 고친 것

  • 요청: 초기 중복 API 제거, 아래쪽 차트는 화면에 들어올 때 요청
  • 렌더: 화면 밖 차트는 마운트하지 않고 순차 렌더, 무거운 차트는 화면에 보일 때 동적 import, 수백 개의 칩을 가벼운 버튼 컴포넌트로 교체
  • 번들: 차트 플러그인을 전역 등록에서 쓰는 컴포넌트 등록으로 옮기고, 무거운 컴포넌트 청크 분리
  • 화면 밀림: 요약 카드·필터·이미지 영역의 높이를 미리 확보
  • 화면 유휴 시점에 미리 불러오는 시도는 TBT를 오히려 악화시켜 되돌렸습니다. 같은 개선을 고객사 배포 코드에도 반영했습니다.

현장 TV 생산 리더보드

생산 라인 입구와 식당 TV에 하루 종일 띄우는 성과 화면입니다. 아무도 조작하지 않고 멀리서 지나가며 봅니다.

  • 지표 편차를 계산해 보니 시간당 생산성은 사람 간 차이가 4.6%뿐이라 생산량 순위는 사실상 투입 시간 순위였습니다. 개인 목표 대비 달성률로 바꿨습니다.
  • 품질 지표 없이 속도 지표만 보이면 꼼꼼히 검사하신 분이 오히려 낮게 평가될 수 있어, 검사원 속도 지표는 뺐습니다. 근거 없는 경고색도 없앴습니다(색 13종 → 6종).
  • 관리자가 쓴 공지가 TV 한 화면을 넘으면 자동으로 줄어듭니다. 줄일 때 폭도 넓어져 높이가 비례하지 않아 이분 탐색으로 배율을 찾습니다. 공지 HTML 정제기와 외부 이미지 SSRF 방어를 직접 구현했습니다.
  • TV 화면에 "미등록 작업자"로 표시된 16명을 사원 명부와 1:1로 대조해 12건이 제 조회 조건 때문임을 찾고, 목록 조회와 판정 기준을 분리했습니다(16 → 4건).
원본 프로토타입은 기획 담당자가 작성했고, 사용자 관점 재설계와 실서비스 구현을 맡았습니다.

검사 공정 주간·야간 생산량 차이 분석

"야간 생산량이 왜 더 높은가"라는 질문을 측정할 수 있는 문제로 바꿨습니다.

  • 오후 물량 집중, 주간 일감 부족, 야간 쉬운 물량, 품질 저하 네 가설을 데이터로 하나씩 폐기했습니다.
  • 1인당 생산량 대신 검사 1건당 걸린 시간으로 비교 축을 바꿨고(주간 약 60초, 야간 약 30초), 주·야를 오가는 소수 인원을 같은 사람 비교로 활용했습니다.
  • 표본이 3건뿐인 항목은 "결론 불가"로 보고했습니다. 민감한 주제라 개인 식별 정보를 빼고 흐름 관점으로 정리했습니다.
결론이 인력 추가가 아니라 검사 외 업무 자동화를 가리켰고, 이미지 회신 자동화의 출발점이 됐습니다.
운영 데이터 · 장애 대응

운영 DB 사고를 적용 전에 막은 일

  • 자동 생성된 마이그레이션에 운영 중인 ID 번호 발급 테이블을 지우는 구문이 들어 있는 것을 적용 전에 발견해 막았습니다.
  • 적용되지 않은 채 커밋만 된 마이그레이션에 컬럼 삭제 수십 건이 있는 것을 버전 테이블·실제 스키마로 교차 확인해 삭제를 권했습니다.
  • 검사 이력 테이블 PK가 INT 최대값에 도달해 저장이 멈춘 장애에서 1.15TB·12개 테이블 규모를 실측하고, 무중단 전환 순서와, 그동안 데이터를 받을 임시 DB의 ID 범위가 겹치지 않게 나누는 방법을 설계했습니다(진행 중).

인터랙션 설계

작은 상호작용을 끝까지 따라간 사례

  • 필터 칩: 클릭 토글은 그대로 두고 제품 번호를 드래그·더블클릭으로 복사할 수 있게 했습니다. 더블클릭의 첫 클릭은 구분할 방법이 없어 세 안의 비용을 비교한 뒤, 잦은 동작에 깜빡임을 주지 않는 250ms 지연을 골랐습니다.
  • 페이지 이동: 마우스를 올린 목록만 방향키로 넘기게 했는데 로딩 중 영역이 사라지며 상태가 굳는 버그가 생겼습니다. 상태를 저장하지 않고 키를 누른 순간 좌표로 판정하게 바꿨고, 회귀 테스트를 일부러 깨뜨려 테스트가 실제로 잡는지까지 확인했습니다.
  • 반응형: 추정으로 고친 CSS가 세 번 실패하자 실측 페이지를 만들었고, 테마 글꼴이 실제로 로드되지 않아 모든 폭 계산의 전제가 틀렸다는 것을 찾았습니다.

사내용 웹을 고객사용으로 전환

  • 사내 전용으로 만든 화면이라 현장 이름·설비·교대 근무 시간·업무 시작 시각 같은 기준이 코드 상수로 들어 있었습니다. 고객사마다 현장 수, 설비 수, 주야간 근무 시각이 달라 그대로는 쓸 수 없었습니다.
  • 고객사 관리자 화면을 만들어 현장·이미지 저장 경로·교대 근무 시간·사용자·검사원 목표 생산량을 웹에서 바꾸게 하고, 화면 집계가 상수 대신 이 설정값을 기준으로 계산되게 바꿨습니다.
  • 설정은 서버 설정 파일과 DB에 함께 저장됩니다. 한쪽만 바뀌는 일이 없게 파일 잠금과 원자적 쓰기를 쓰고, 실패하면 DB를 롤백하고 설정 파일도 원래대로 되돌립니다.
  • 고객사에 나가는 화면이라 디자인과 반응형도 함께 다듬었습니다.

AI 활용과 기술

AI는 구현 속도를 위해 쓰고, 설계와 검증의 책임은 직접 집니다.

AI 활용 방식

작성은 AI와 나누고, 판단과 검증은 직접

  • 집계 기준과 구조 설계는 Claude, 반복 구현은 Codex·Cursor로 나눴습니다. 확정된 사양은 함정과 검증 절차까지 적은 지시서로 맡기고 결과를 검수했습니다(현재는 팀 정책으로 Claude로 통일).
  • 작업마다 확정·미확정·반려 목록을 담은 단일 기준 문서를 두어 여러 도구가 같은 기준으로 일하게 했습니다. 고객사 분기 규칙 문서는 AI 도구 설정에 연결했습니다.
  • 결과는 DB 실측, 실제 렌더 측정, 산출물 비교로 확인합니다.
  • 운영 문서도 AI가 읽는 형식(저장소 규칙 문서·운영 런북)으로 남겨, 다른 사람이 AI에게 맡겨도 같은 기준으로 일하게 했습니다.
  • 재현성이 중요한 메일 파서는 AI 대신 규칙 기반으로 만들었습니다. 토큰과 비밀번호는 지우거나 가린 뒤 공유합니다.
